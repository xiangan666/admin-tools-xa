二改作者：相安  
联系邮箱：3199912548@qq.com

## 数据结构

规则作为已有家园或传送点对象的 `rules` 字段保存。没有 `rules` 的旧存档使用不冷却、不收费、全天允许的默认值，不强制修改旧数据。

本版沿用2.4.0引入的双层家园策略，2.5.0起由管理员统一设置。家园保留独立的房主 `rules`，另按策略读取服务器附加规则。执行是**先满足服务器层，再满足房主层，两层都必须通过**；不把服务器值覆盖进房主对象。公共传送点保持单层规则，不参与家园收益结算。

```json
{
  "x": 100,
  "y": 64,
  "z": -200,
  "dimension": "minecraft:overworld",
  "destinationId": "由创建逻辑生成并在覆盖坐标时保留的稳定标识",
  "teleportEnabled": true,
  "rules": {
    "cooldownSeconds": 60,
    "cost": { "typeId": "minecraft:diamond", "amount": 2 },
    "timeWindow": { "enabled": true, "start": "22:00", "end": "06:00" }
  }
}
```

| 字段 | 含义 |
| --- | --- |
| `cooldownSeconds` | 0–86400 的整数，单位为现实秒；0 不限制冷却。 |
| `cost.typeId` | 配置时玩家当前背包中选择的物品类型 ID；支持附加包物品。收费按类型，不按自定义名称或附魔区分。 |
| `cost.amount` | 0–2147483647 的整数；0 不收费。实际数量不足时拒绝传送。 |
| `timeWindow.enabled` | 是否启用游戏时段限制。 |
| `timeWindow.start/end` | 严格 `HH:mm`，范围 00:00–23:59。包含开始时刻、不包含结束时刻；开始大于结束时跨午夜；开始等于结束时全天允许。 |
| `destinationId` | 删除后重建生成新的 ID，覆盖已有家园坐标时保留，以免旧目的地冷却套用到新目的地。 |
| `teleportEnabled` | 仅家园使用，由管理员设置；缺省为true。false阻止房主和访客的该家园传送，不受规则总开关影响。 |

Minecraft 游戏时钟以 `world.getTimeOfDay()` 为准：0 tick = 06:00，6000 = 12:00，18000 = 00:00。时段限制不使用操作系统时区或现实钟点。

## 接口

- `normalizeRules(value)`：规范化规则，拒绝非法数值和时刻。
- `showTravelRules(player, { kind, getDestination, saveRules, manageAsAdmin? }, back)`：家园使用 `kind: "home"`，传送点使用 `kind: "warp"`；`getDestination()` 每次返回最新目的地，`saveRules(rules)` 必须检查权限和世代。`manageAsAdmin` 同时校验管理员身份，可预编辑暂停的房主规则，不改变全局开关。
- `startRuleTeleport(player, descriptor, back)`：返回 `Promise<boolean>`。`descriptor` 包含 `kind`（`home` 或 `warp`）、`ownerId`、`name`、`getDestination()`，可选 `authorize()`、`onSuccess()`。
- `teleportPlayer(player, location, options)`：兼容上游调用方式，同时返回永不拒绝的 `Promise<boolean>`；其 `beforeTeleport()` 与 `afterTeleport(success)` 是内部事务回调，传入原生 `player.teleport()` 之前会剔除。

`authorize()` 必须同步返回严格的 `true` 才能放行。`onSuccess()` 在真正的玩家传送成功后同步执行，用于扣减家园授权次数；失败、取消和移动中断不调用。

## 执行顺序和成功定义

1. 同一玩家同时仅允许一个受规则约束的传送，涵盖条件确认窗、坐骑选择、倒计时和实际移动阶段。
2. 发起时构建条件说明，显示目的地与坐标、当前游戏时刻、授权状态、每层时段/冷却状态及合计费用和背包数量。玩家确认后才继续；取消不扣费。
3. 确认后检查目的地、授权、维度锁；家园先检查服务器层的时段、冷却和费用，再检查房主层。两层同类型收费按合计数量核对，不重复使用同一库存。确认窗打开期间条件发生变化时，后续检查拒绝旧确认。
4. 沿用全局 `tpaDelaySec` 倒计时以及移动超过 0.5 格或切换维度取消的行为。进入等待立即显示聊天提醒、中央倒计时、目的地与移动取消警告；动作栏每5刻刷新，标题每秒更新，结束清理；0秒延时不显示等待。坐骑仍沿用上游确认界面。床、死亡返回及TPA共用相同提示，TPA双方都要保持不动，但这些功能不读取某个家园的收费规则。
5. 倒计时结束后重新读取规则；骑乘导致移动推迟到下一 tick 时，在实际移动所在 tick 再检查一次。目的地已经修改时拒绝使用旧坐标。
6. 同一同步调用中记录原物品堆、扣除启用的费用、为房主层收费准备不可领取的收益预留，再调用原生玩家传送。扣费中途或收益预留失败会恢复此前扣除的物品。玩家传送失败时取消收益预留、原物品堆原位退还；如其他扩展占用槽位，则尝试加入背包，剩余物品以原 `ItemStack` 掉落到玩家脚下并提示。
7. 仅玩家原生传送成功后记录冷却、提交房主税后收益并调用 `onSuccess()`。房主税率默认30%、管理员可设置0–100%，小数税额按房主及物品类型累计。坐骑或鹦鹉是伴随对象；其无法跟随不会把已经成功到达的玩家重新算作失败，也不会重复收取费用或扣减授权次数。

退款使用原 `ItemStack.clone()`，保留自定义名称、附魔、耐久、备注等堆栈数据；不会根据类型 ID 重建退款物品。

服务器规则总开关及冷却、收费、时段开关仅影响家园对应两层规则，不关闭访问授权，不删除已有房主配置。房主收费的净物品入账；服务器附加费用与税额独立消耗。收益需要安全序列化，无法可靠恢复特殊数据的收费物品会拒绝本次结算并退款。领取背包满时保留账本余额，不使用传送退款的掉落回退方式。完整说明见 [家园收益说明](HOME_REVENUE.md)。

## 冷却持久化与异常边界

每个玩家自己的动态属性中，按 `[目的地类型, 家园主人 ID, 目的地名称, destinationId 或 legacy]` 保存成功时间。属性名使用双散列缩短，并在值内保存完整身份以检测碰撞。不同玩家、不同家园、不同传送点分别冷却；关服和离线期间现实时间仍继续计算。覆盖家园坐标保留 ID 和已有规则。

冷却存储写入若在成功传送后失败，向玩家告警，并以内存记录继续约束当前会话；服务器重启后无法恢复此前未成功写入的记录。授权次数存储回调失败同样只报告异常，不能把已发生的成功传送改判失败而退费。家园授权模块负责该情况下的后续拒绝访问或人工恢复。

收益预留与领取有持久化和防重保护；异常退出留下的未确认预留不自动计为可领取收入。已真实成功移动后的入账失败需要核对，不将其改判为失败退款。详细异常边界见 `HOME_REVENUE.md`。

Minecraft 脚本 API 不提供跨背包、坐标、世界/玩家动态属性的原子事务。正常 API 返回失败、移动取消、权限撤销、数量不足等路径有退款和不启动冷却的自动化测试；操作系统强杀、崩溃、存储损坏，或退款时所有背包写入及掉落 API 同时失效，不承诺自动回滚。生产服务器应保留世界备份。
